## What the Reports workspace owns

**Reports** coordinates authorized report requests, exact infrastructure
scope, format validation, asynchronous generation, artifact storage,
schedules and delivery. KAORI normalizes committed evidence from
infrastructure domains; Reports is not an alternative provider
for Kubernetes or Object Storage facts.

Report rendering and long-running generation are owned by
canonical background workers and JobExecution. A page request
must not fabricate completed artifacts or run a report renderer
in the HTTP process.

## Menu and access

The source catalog defines the following Reports capability tabs:

- **Overview:** `reports.view`, for reporting coverage, worker
  posture, artifact storage readiness and configuration boundaries.
- **Generate:** `reports.generate`, for a scoped new report
  request subject to server-side admission.
- **Generated:** `reports.view`, for accepted artifact
  records, status, permitted details and retrieval.
- **Templates:** `reports.manage_templates`, for
  source-qualified template registry or management.
- **Storage:** `reports.manage_storage`, for authorized
  artifact storage readiness and configuration.
- **Schedules:** `reports.manage_schedules`, for
  registered periodic execution and delivery settings.

These are navigation permission labels. Actual backend routes,
resource scopes, active features and role restrictions must
be verified for the accepted Application candidate. Access
to Generated Reports does not authorize changing storage,
templates or schedule execution.

## Task: assess reporting readiness

1. Open **Reports → Overview** with the relevant permission.
2. Review the requested infrastructure domain and exact asset
   context. Do not assume a default or cross-cluster scope.
3. Inspect the **Reporting Operational Posture** for worker
   queue availability, active schedules, storage readiness,
   recent demand and generation completion quality.
4. Review the reported **Report Coverage & Artifact Estate**
   and **Contracts & Automation** sections.
5. Distinguish a catalog-declared report from an admitted,
   executable report contract. Reserved/future coverage is
   not a successful generator.
6. If the queue, data collection or storage is unavailable,
   treat the corresponding operation as **degraded or
   blocked**, not Ready.

**Expected result:** a read-only understanding of which
report contracts and dependencies were actually qualified.
A displayed worker-ready state is source evidence, not
proof that every future task will complete.

## Task: request a report safely

The source catalog defines supported output families
including Analytics **PDF, XLSX and CSV** and Inventory
**XLSX and CSV**. The concrete report type controls which
sections and formats are available. A format offered in
one domain is not automatically valid in another.

1. Open **Reports → Generate** with `reports.generate`
   and the resource scope granted to your account.
2. Choose the exact report family and accepted report
   type from the active source-controlled catalog.
3. Select **one canonical infrastructure asset scope**:
   one Kubernetes cluster with an optional namespace,
   or one registered Object Storage system, as allowed
   by that report type.
4. Select only available sections, time period and
   output format. Never infer support from a planned
   catalog entry or force a hidden parameter.
5. Review the request summary, scope and potential
   artifact sensitivity before submitting a permitted
   generation command.
6. Once accepted, monitor the canonical JobExecution
   or Generated Reports record. Submission is not
   proof of successful artifact publication.
7. Only retrieve an artifact after the generation
   and storage evidence are committed and your
   access to that record is confirmed.

**Expected result:** an authorized, asynchronous report
request with observable outcome and artifact lineage,
or a clear validation/permission/dependency rejection.
There is no implicit fallback to a different cluster,
report family, renderer or destination after submission.

No live report is generated by following this written
example; operator action requires an accepted App RC
and environment-specific authorization.

## Generated artifacts and failure states

**Reports → Generated** presents artifact records with
their own generation status, storage location authority,
retention and archive evidence. Use these distinctions:

- **Queued or running:** the worker has not finished.
  An apparent active job is not a finished file.
- **Generated but not published:** generation may have
  succeeded while artifact storage failed or remained
  degraded; verify the accepted lifecycle.
- **Available:** an accepted, authorized artifact exists
  in the owning storage backend for permitted retrieval.
- **Failed or unavailable:** inspect the sanitized
  JobExecution and storage readiness, not a guessed
  external provider success.
- **Archived or expired:** storage and retention policy
  may restrict further access; no hidden link should
  bypass the owning archive policy.

Generated records and downloadable artifacts can
contain sensitive infrastructure context. Follow
your organization's data handling and retention
controls; do not paste report URLs or contents into
public issue descriptions.

## Storage, templates and schedules

**Templates** must be validated against the report
catalog. A custom template cannot silently introduce
an unsupported section or change the allowed format.

**Storage** readiness is a shared, multi-process
operational state. Background refresh publishes
the last observation, backend state and availability.
A page visit should not independently contact
S3-compatible object storage to manufacture Ready.
If state expires, present stale or unknown evidence.

An authorized **Verify Storage** action is different
from opening the Storage page: the source workflow
performs a short-lived write, read, delete verification
and requires proper mutation permission and change
assessment. Never run it merely to make a dashboard
metric green.

**Schedules** coordinate eligible report requests
and delivery intent; actual dispatch uses background
workers and accepted provider/channel configuration.
A saved schedule is not proof of successful future
delivery or recipient authorization.

## Troubleshooting and escalation

- If a report type is missing, verify the canonical
  catalog and accepted domain/scope instead of
  supplying a manually invented identifier.
- If Generate rejects a selection, check authorized
  cluster/system scope, report sections, period,
  output format and server-side validation evidence.
- If a job is pending, distinguish worker/queue
  readiness from storage and provider facts.
- If an artifact is absent, inspect the owning
  generation and storage lifecycle separately.
- If an exported file cannot be retrieved, confirm
  current user scope, artifact status and archive
  policy before assuming the file was lost.
- If a schedule appears idle, inspect the scheduled
  dispatch and eligible delivery channel without
  exposing recipients or credentials.

Report failures should provide sanitized operational
feedback with a specific generation/job reference.
Do not bypass report permissions, manually rewrite
artifact storage metadata or trigger unrelated
provider mutations to recover a failed report.

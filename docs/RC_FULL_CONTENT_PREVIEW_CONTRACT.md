# Full-content documentation RC review contract

**Authority:** Docs #131, coordinated with coverage #127, stable versioning #15, rights #74 and the existing signed release/deployment process #13/#14.

**Status:** Reviewed design proposal only. No full-manual RC route, accepted candidate article set, new signed image, public deployment, Human UAT or stable KAORI release is authorized by this text.

## Requirement and publication boundary

The maintainer wants a complete KAORI software manual available for real browser review before accepting the first Application and Docs stable `v0.3.0` releases. The intended manual covers architecture, installation and runtime modes, capability menus, role permissions, integrations, safe operations, reference, troubleshooting and compatibility.

Current `docusaurus.config.ts`, `docs/CONTENT_SAFETY.md` and issue #15 withhold native product pages until the documented Application release is accepted. Existing `content/` articles remain `draft: true`, `docs/PUBLISHED_VERSIONS.json` remains `awaiting-release`, and `versions.json` has no published versions. The public Home and isolated conceptual `/rc-review` walkthrough do not replace an accepted full manual.

A candidate-specific full-manual route requires **new explicit editorial and public-rights approval**. Do not silently activate all drafts to satisfy the request.

## Proposed Docusaurus route policy

- **Home `/`:** Continue to show the existing release-neutral orientation.
- **Conceptual `/rc-review`:** Keep the separate approved conceptual walkthrough, with no product version claim.
- **Candidate manual `/review/`:** Use the existing native Docusaurus docs plugin and autogenerated sidebar for an explicitly admitted, candidate-scoped article set only after approval.
- **Stable `/v0.3/`:** Continue to withhold until an actual stable Application `v0.3.0` release and accepted Docs snapshot under #15.
- **Patch notes `/releases/v0.3.0/`:** Keep governed by release-notes owner #9 and actual stable evidence.
- **Search:** Keep unapproved candidate and stable content out of public indexes; issue #16 owns release-qualified search.

The candidate route is a review surface, not an alternative stable version, a second host, a second documentation engine or a new deployment slot. Do not redirect prerelease URLs to stable content or create false canonical support claims.

## Separate Application and Docs identities

Every admitted candidate article must identify the **accepted KAORI Application prerelease candidate** separately from the **KAORI Docs image RC**. The application identity requires an actual authorized source/tag and associated source, image and manifest evidence. A development `VERSION` string or `kaori/staging` head alone is not release proof.

The Docs identity requires the exact reviewed source commit, issue and reviewer acceptance, signed image digest, publication authority and actual runtime receipt after a separately approved deployment. Content quality, Application behavior maturity and deployed image authenticity must remain independently testable.

## Candidate article admission

1. Use the existing `content/` tree as the only native public-article source. Do not copy unpublished guides into `src/pages/`, `static/` or internal engineering paths.
2. Review every candidate article against the exact Application source, the domain owner, actual permissions, capability maturity, safe workflows and known unsupported scenarios.
3. Record the editorial issue/PR, accepted Docs source, rights and screenshot attribution, source applicability and meaningful UAT evidence for every included chapter.
4. Use an explicit fail-closed **candidate inclusion manifest** separate from stable `docs/PUBLISHED_VERSIONS.json`. The manifest is an allowlist and evidence reference, not authority to self-approve publication.
5. Exclude unpublished `draft: true` articles from production output. Change an accepted article to `draft: false` only in a separately reviewed article PR with its valid candidate approval reference.
6. Reject unknown article paths, private engineering material, unapproved host or customer data, unsupported Application identity, unqualified screenshots and any unexpected stable routes.
7. Show an unmistakable prerelease applicability notice and honest evidence/maturity limitations in the candidate manual. Do not imply all menus are production-ready merely because their catalog entry exists.
8. Keep unapproved articles out of static output, the sitemap, metadata, link indexes and search. Candidate URLs must not masquerade as supported `/v0.3/` stable canonical URLs.

Rights issue #74 must approve original public prose, contributor permissions, asset licenses, trademark boundaries, sanitized visuals and third-party material before any full-content RC article is made public. This condition also applies to a publicly accessible prerelease site.

## Implementation boundary

The bounded technical implementation authority is issue #142, **blocked until** the #131 publication decision and relevant #74 rights conditions are accepted. The implementation must reuse the existing Docusaurus preset/sidebar and approved build/test/deploy workflows.

No new router, version resolver, validation service, reverse proxy, DNS, VPS, build registry, release engine or production deployment trigger is permitted. Signed candidate publishing remains manual, immutable and conditioned on the exact independently admitted staging source and approval.

The existing stable version resolver must continue to reject an empty or unqualified published mapping. Candidate applicability must not satisfy #15 stable release checks.

## Browser and content acceptance

- Confirm the documented domain, menu and nested-tab coverage against canonical Application navigation, effective permissions and actual accepted candidate UAT, not just source-defined links.
- Prove the candidate sidebar resolves every approved article and does not expose unknown, draft, internal or private sources.
- Verify six canonical viewport widths, light/dark, keyboard focus, accessibility, 200% zoom, deep links, link integrity, true 404 behavior and responsive article navigation.
- Include positive and negative tests for content publication, stable URL absence, search/sitemap leakage, permissions, source freshness and unsupported features.
- Require exact-head Developer Check, independent review, merged-SHA Full Admission, Container Admission, Browser Quality Evidence and documented admission receipt.
- Generate a separately approved signed immutable Docs RC artifact and use the **existing single Docs public slot** with exact SHA/tag/digest swap authorization, rollback and shared-edge validation.
- Require direct HTTPS browser testing of the actual public candidate route, evidence of the observed image and explicit Human Acceptance.

A source build, CI green status or GitHub Release record alone is not proof of deployed public documentation or editorial acceptance.

## Separate stable graduation

1. Confirm the accepted KAORI Application `v0.3.0` stable release, signature, tag, source, image, manifest and operator/Human Acceptance.
2. Confirm the complete documented product scope and all approved menu/workflow guides, sanitized rights and accepted Docs browser UAT.
3. Freeze a native Docusaurus `versioned_docs/version-v0.3/` snapshot, native sidebar, exact patch release notes and accepted source-to-product mapping under #15 and #9.
4. Admit version-isolated search under #16 only for actual authorized published content.
5. Follow Docs staging, human review, promotion PR to `main`, immutable stable artifact, approved production deployment and independently verified rollback. Merging `main` does not release production.
6. Retire or explicitly qualify obsolete candidate routes according to a reviewed redirect and documentation lifecycle policy.

This design does not change current stable, public RC deployment or Application behavior. Before #142 activation, reconcile its implementation contract with approved content safety and rights documentation rather than claiming a new authority from a proposed Markdown file.

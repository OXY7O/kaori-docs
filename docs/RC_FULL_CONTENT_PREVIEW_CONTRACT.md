# Full-content documentation RC review contract

**Authority:** [Docs #131](https://github.com/OXY7O/kaori-docs/issues/131), coordinated by [Docs #127](https://github.com/OXY7O/kaori-docs/issues/127) and the existing [Docs #15](https://github.com/OXY7O/kaori-docs/issues/15) publication/version contract. **Status:** implementation proposal for independent review, **not yet a published or approved full-content Docs RC**. Initial review 2026-11-23.

## The requirement and current conflict

The maintainer wants to inspect a **complete KAORI software manual in a working web RC**, spanning architecture, installation, configuration, every supported menu, provider integrations, procedures, RBAC, maintenance, reference, troubleshooting, and compatibility. Both **Docs** and **KAORI Application** must receive complete independent acceptance before the first stable `v0.3.0`.

Currently, `docusaurus.config.ts` enables native public product documentation **only** for stable Application Major.Minor lines admitted by `docs/PUBLISHED_VERSIONS.json`. The empty mapping correctly withholds `/v0.3/`. The 15 existing article drafts in `content/` are `draft: true`; production RC.9 publicly shows only the release-neutral Home. The isolated conceptual `/rc-review` page added later is useful but cannot substitute for full-manual RC UAT.

The established `docs/CONTENT_SAFETY.md` says pre-stable material must remain draft and hides the product guide corpus from public builds. **This proposed contract requires a separately reviewed authority update before any candidate article appears on the public site.** It does not silently relax #15 stable publication guarantees or turn the full draft tree on.

## Proposed decision: native, explicit candidate-only documentation mode

For the existing single-slot, signed Docs **prerelease** image only, use Docusaurus' **existing docs plugin and autogenerated sidebar** to expose **reviewed candidate chapters** under a distinct, explicit `/review/` route. Do not add a custom router, a second application/version engine, a separate host, or a second Docs deployment slot.

| Public content state | URL/surface | Inclusion rule |
| --- | --- | --- |
| Release-neutral Home | `/` | Existing approved Home, always distinct from Application release qualification |
| Conceptual learning preview | `/rc-review` | Existing independently reviewed page; not a product manual or stable version |
| **Candidate full manual** | **`/review/`** and native nested article paths | Only *explicitly approved, source-pinned, public-safe* candidate articles after #131 implementation gates and human sign-off |
| Stable product manual | `/v0.3/` and native frozen versioned subroutes | Only after **accepted Application stable `v0.3.0`** and #15 authentic release/source/digest snapshot approval |
| Exact patch release notes | `/releases/v0.3.0/` | #9 first-stable patch-note authority only |
| Local search | Disabled during initial candidate mode | #16 permits search only for correctly scoped accepted content; never search all drafts/private engineering files |

An article in `/review/` means **review-ready candidate documentation**, not stable, GA, guaranteed compatible, or proof of working provider integrations. The scope label should include **KAORI Application RC applicability** and **Docs independent RC artifact identity**, never conflate the two. Public URLs must be unambiguously prerelease and must not redirect or canonicalize to stable `/v0.3/`.

### Admission boundaries for the candidate corpus

1. A current **application candidate** must be identified by an actual accepted KAORI Application prerelease tag/source SHA and its governed manifest/digest evidence. Merely seeing `kaori/staging` or a `VERSION` file is insufficient. Its accepted UAT scope defines what the reader may be instructed to do.
2. Each proposed article receives an **explicit content approval record** with Docs owning issue/PR/SHA, named reviewer, App source+capability contract, applicability, permission/audience, rights/sanitization, known gaps and real testing outcome. A chapter can be shown as conceptual with limitation notices without falsely claiming completed practical UAT.
3. The implementation must introduce a **small review inclusion manifest**, distinct from `PUBLISHED_VERSIONS.json`, listing only accepted candidate article paths and candidate applicability. Fail closed if a production candidate build finds an enabled article absent from that manifest, an accepted entry still marked `draft: true`, a private/internal path, an unverified application identity, or an unexpected native version/snapshot. **Do not** make the manifest itself an authority for acceptance; independently verify its signed source and approval evidence.
4. The `content/` editorial source remains the single article source for Docusaurus. Work in issues #2–#9 and #128–#130; **do not duplicate drafts into `src/pages/`**, clone the content tree, or serve internal `docs/` files. Once a chapter is independently reviewed for **candidate** publication, its issue-owned PR may change it from `draft: true` to `draft: false` only together with an accepted allowlist and source/maturity/rights evidence. Remaining articles stay `draft: true` and are excluded.
5. Reuse Docusaurus native docs/sidebar/build. The **RC candidate** preset selects the same content root at an explicit `routeBasePath: 'review'` only when the reviewed candidate manifest has been admitted and the normal protected signed RC build is authorized. It must not enable candidate mode during an unapproved ordinary production build, accidentally include local editorial preview, or affect stable published snapshots.
6. Preserve `docs/PUBLISHED_VERSIONS.json` as `awaiting-release`, `versions.json` as `[]`, no fake dropdown, no `/v0.3/` alias, and no patch-note route until the independent stable release mapping. The published-version parser remains authoritative for stable lines and must not accept candidate RC identity as its stable proof.
7. Public candidate docs must show a persistent **pre-stable/not production-certified** notice, readable app candidate identity and evidence limitations. Authored examples must be synthetic and non-operationally harmful; screenshots and diagrams require approval and accessibility descriptions. No private host, registry/project ID, credential, UAT receipt or customer source details in tracked files.
8. Candidate pages should carry appropriate search-engine `noindex` and prerelease canonical metadata pending separate SEO/content policy review; Home canonical stays Home. Broken and cross-version links are build failures, not silent redirects.

### Separate implementation and authority decision

This document is **design proposal only** under #131. Before changing `docusaurus.config.ts`, `src/versioning/publication.ts`, `docs/CONTENT_SAFETY.md` or exposing an article:

- Confirm the mode against current approved Docs #15 and #74 licensing/rights, adjust the authority documents through a separately reviewed issue-scoped PR, and obtain reviewer/owner acceptance for the candidate publication contract.
- Divide implementation into a bounded native Docusaurus candidate-route/manifest/negative-test PR and independently owned article-approval PRs. Both must preserve the existing stable version and public-safety gates.
- Reuse existing release, admission and browser checks. Extend existing output-boundary/route tests for candidate allowlist and stable isolation; **do not build a parallel release workflow or custom validation service**.
- Keep automated RC publishing **opt-in/disabled** unless separate exact-source owner approvals and #74 rights conditions are met.

## Acceptance: content and browser

The RC is ready for **human editorial UAT** only when:

- [ ] The master coverage matrix #127 and complete catalog #130 map all source-defined menu views to reviewed pages or explicit pending/unsupported declarations; no silently missing sections are called complete.
- [ ] Each approved manual chapter has correct app candidate applicability, role/provider prerequisites, navigation, safe steps and expected evidence, limitations, error/empty/freshness behavior, rollback where relevant, and rights/sanitization.
- [ ] The candidate route and autogenerated sidebar show only allowlisted article pages; unknown/draft/unapproved/private paths are proven absent from static output, sitemap, link index and search.
- [ ] Browser QA covers six canonical viewports, light/dark, menu/article navigation, keyboard/focus, axe, 200% zoom, deep links, 404 and breakage across sections.
- [ ] The signed Docs RC tag/source/image digest matches exact staging admission, separately approved for the **single existing Docs slot** under #13/#14/#43, with all-site shared-edge validation and rollback.
- [ ] Real public HTTPS test of `https://docs.kaori.cloud/review/`, observed image receipt, UAT screenshots, rights/operational owner and **explicit Human Acceptance**. A successful `npm run build`, CI or published GitHub Release does not substitute for live web proof.

## Stable graduation (separate release)

Once both systems are accepted:

1. Verify **KAORI Application `v0.3.0` stable release**: actual signed manifest, accepted tag/SHA/digest, UAT and human release authority under KAORI #4198.
2. Complete all documented in-scope menu/workflow guides and installation/security/operations chapters with release applicability and accepted user validation.
3. Independently freeze the approved native Docusaurus `versioned_docs/version-v0.3/` snapshot and sidebar under #15, approved mapping in `PUBLISHED_VERSIONS.json`, exact patch notes #9, and version-isolated search #16.
4. Follow accepted Docs staging → source promotion PR to main → signed immutable Docs stable publication **without rebuilding an unaccepted artifact** → separately governed stable deployment and rollback/Human Acceptance. A main merge alone does not release production.
5. After stable acceptance, keep any historical candidate review links explicitly marked or retired per the approved URL/redirect policy; never let an old candidate route pretend to be current stable.

## No new authority claimed

This proposal does not authorize RC route activation, article publication, removal of stable version/safety gates, changing a GitHub Environment, releasing the Application or Docs stable, mutating the VPS, or creating a second docs.kaori.cloud host. It is a **reviewable design input** for implementation authority; the existing issue/PR, licensing, CI, admission and Human Acceptance gates remain mandatory.

# KAORI Docs CI/CD

This is the Docs-specific implementation of [KAORI Engineering Delivery](https://github.com/OXY7O/KAORI/blob/main/docs/engineering/KAORI_DELIVERY_WORKFLOW.md) and the [KAORI Website CI/CD contract](https://github.com/OXY7O/kaori-website/blob/main/docs/CI_CD.md). It does not alter Application or Website workflows.

## Runner eligibility (must be verified live)

| Workflow                                   | Runner label set                       | Authority                    |
| ------------------------------------------ | -------------------------------------- | ---------------------------- |
| Developer Check: Route Checks              | `ubuntu-24.04`                         | Issue-branch and fork denial |
| Developer Check: Docs Validation           | `self-hosted, linux, x64, platform-ci` | Trusted source validation    |
| Full Admission: promotion policy           | `ubuntu-24.04`                         | Fail-closed staging-to-main  |
| Full Admission: static, container, browser | `self-hosted, linux, x64, kaori-ci`    | Trusted admitted source      |
| Release Candidate (#13, manual-only)       | approved release runner                | Human release authority      |
| Release Deployment (future #14)            | approved SSH/deploy runner             | Signed digest and host trust |

**The runner group must explicitly allow the public `OXY7O/kaori-docs` repository for trusted jobs.** Public visibility and matching labels do not grant runner-group access. Verify in GitHub repository Settings → Actions → Runners and organization runner groups, then require a real successful action run; do not repurpose/deregister the Application or Website runners. If CI remains queued, record BLOCKED rather than claiming PASS.

## Developer Check

`.github/workflows/developer-check.yml` is triggered on same-repo pull requests targeting `kaori/staging` (Draft and Ready). It verifies the canonical `kaori/<type>-<issue>-<slug>` branch; runs `git diff --check`; classifies changed paths and fails closed on unknown paths. Public site/source/configuration/workflow changes require committed lockfile, Node `22.23.2`, `npm ci`, Prettier, TypeScript `tsc --noEmit`, Docusaurus build and static boundary checks. Dependency authority changes additionally run `npm audit --audit-level=high`. An internal-only prose change avoids expensive full build; the routing job remains mandatory.

A lockfile cannot be generated by pretending `npm install` was `npm ci`. The #11 bootstrap lockfile was generated on the authorized self-hosted runner, reviewed, and committed to the combined #11/#12 branch. Developer Check now **only validates** the committed lockfile via `npm ci`; dependency updates must be issue-owned and re-admitted, with no automatic source mutations inside CI.

## Staging Full Admission

`.github/workflows/quality.yml` runs on pushes to `kaori/staging` and `main`; promotion PRs into `main` are allowed only from same-repo `kaori/staging`. Manual invocation is limited to those two refs and may require an accepted default-branch workflow bootstrap. Draft promotion PRs do not execute expensive admission until Ready.

A successful staging Full Admission must include:

- `Full Admission`: exact-source checkout, pinned Node, lock install, format, TS, npm security audit, production build, public output boundary.
- `Container Admission`: actual production-image runtime verification when a production `Dockerfile`/deploy adapter exists; otherwise explicit **NOT APPLICABLE** during #11/#12 foundation, never an image runtime PASS.
- `Browser Quality Evidence`: Playwright + axe in the existing pinned Microsoft browser image, all six KAORI viewport widths in two real color modes, responsive overflow, navigation, theme toggle, keyboard and WCAG automated rules. Attach screenshots/traces/results to exact run. Manual zoom and screen-reader review remain additional human acceptance.

The browser container uses the same bounded self-hosted checkout ownership-repair pattern currently documented for the Website. It requires Docker access on `kaori-ci`; verify available image, runner permissions, and executor isolation before marking PASS. There is **no host service or application deployment** in this workflow.

## Release/deployment boundary

The four canonical workflow names remain **Developer Check**, **Full Admission**, **Release Candidate** (#13), **Release Deployment** (#14). The #13 publisher authority and activation conditions are documented in [Immutable Release Candidate](RELEASE_CANDIDATE.md). The latter two must not be replaced with push-to-deploy scripts. Release Candidate requires separate repository-scoped registry metadata/secrets (#10), exact admitted SHA, signature, digest, vulnerability scan, SPDX SBOM and provenance. Release Deployment requires that accepted immutable candidate, manual approval, pinned SSH host identity, isolated `/opt/kaori-docs` runtime, health and verified rollback. Public `docs.kaori.cloud` DNS/TLS/shared-edge registration is separately authorized.

CI PASS on the self-hosted staging runner is **not staging VPS UAT**, browser Human Acceptance, stable main promotion or deployment verification.

## Untrusted community PR runner boundary (#78)

External fork PRs to `kaori/staging` receive read-only hosted
`Community Fork Check` feedback, **not** trusted admission.
The canonical required `Route Checks` also runs on hosted
`ubuntu-24.04` and **fails** a different-repository source in its
first step before any checkout. This is necessary because GitHub
considers a job-level `skipped` conclusion successful for branch
required-check purposes; skipping alone does not reject the fork.
`Docs Validation` remains on the trusted self-hosted runner and
depends on successful Route Checks.

For PRs targeting `main`, `Promotion Policy` runs on hosted
`ubuntu-24.04` and **fails** sources other than same-repository
`kaori/staging`; its existing step guard is retained.
All privileged Full Admission, container, browser and evidence jobs
remain downstream of that policy. Current push/manual event
authorization and release authority are unchanged. GitHub Admin
must separately verify enforced review and status-check rulesets;
this patch makes no Settings changes.

Do not count skipped jobs as PASS or hosted fork feedback as UAT.
Live external-fork negative testing, Full Admission and Human
Acceptance still require independent execution and evidence.

## Gate failure/recovery

1. Pin failing run URL, exact SHA, failing job, dependency and action versions.
2. Repair only the issue-owned work branch; do not bypass `npm ci`, dependency audit or browser failures.
3. Run a new exact-head Developer Check; review and merge to `kaori/staging`.
4. Collect the merged SHA Full Admission and browser artifacts. Runtime prerequisites absent for a release remain HOLD.
5. After issue #13/#14 and #10 security/preflight are complete, perform separate manual deployment with immutable rollback evidence, then human UAT before promotion.
